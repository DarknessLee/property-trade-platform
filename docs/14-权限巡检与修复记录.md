# 权限巡检与修复记录（E4.1）

- 日期：2026-11-02
- 触发：演示反馈「经纪人账号访问 菜单-资金监管，接口 `/api/escrows/overview` 返回 403」
- 结论：属于**菜单可见性与接口角色不一致**；已修复，并对 6 个演示账号做了逐菜单巡检，另发现并修复 2 处同类问题

## 1. 缺陷与修复

| # | 现象 | 根因 | 修复 |
| --- | --- | --- | --- |
| 1 | 经纪人 → 资金监管：`GET /api/escrows/overview` 403 | 菜单对 agent 开放，但 overview 路由 `@Roles('store_manager','finance','admin')` 漏了 agent | 路由增加 `agent`；`contractScopeWhere` 已按经纪人本人合同范围统计，不扩大数据可见性 |
| 2 | 卖家（C 端）→ 我的：`GET /api/showings/my` 403 | PortalMine 对所有角色都请求带看列表，但预约只对买方开放（M3 设计，测试亦要求卖方 403） | 前端：仅买家请求带看；卖方不显示「预约看房」按钮并提示；后端维持 buyer-only（权限收紧，不回退） |
| 3 | 财务 → 合同签约/交易进度：点击「电子签署 / 作废 / 更新进度 / 提醒」才 403 | 菜单对 finance 开放用于只读查看，但页面按钮未按角色隐藏，接口按后端策略拒绝财务写入 | 前端按角色隐藏写操作入口（合同签署/作废仅 agent/store_manager/admin；进度更新/提醒对 finance 隐藏），后端保持拒绝 |

## 2. 巡检方法与结果

新增两个回归用例：

- `e2e/permission-audit.spec.ts`（6 条）：登录 **admin / finance / store_manager / agent / buyer / seller** 六个演示账号，遍历其可见 B 端菜单（含新页面）与 C 端核心页面（首页/找房/地图/我的/房源详情），收集所有 `/api/**` 响应，断言 **无任何 4xx、无页面 JS 异常**；C 端卖家页面不触发买方专属接口。
- `server/test/permissions.spec.ts`（4 条）：固化「菜单可见 ↔ 接口可用」关键组合：经纪人 overview 200、卖家带看 403（设计如此）、财务合同/进度写操作 403、卖家预约 403。

## 4. 约定（防止回归）

1. **菜单开放 = 至少只读接口可用**：新增菜单项时必须同步检查该页首屏所有 GET 接口的角色列表。
2. **只读角色（财务）不显示写操作按钮**，后端继续按最小权限拒绝写接口。
3. 新页面/新接口加入 `permission-audit` 或 `permissions.spec.ts` 覆盖，`npm run verify` 门禁内执行。
4. 数据范围仍由 `contractScopeWhere/resolveScope` 控制：放开接口角色不等于放开数据范围（经纪人仅本人、店长本店、财务机构）。
